## Цель

Подготовить реляционную схему PostgreSQL для заявок на пересдачу, заполнить
её учебными данными и написать запросы с фильтром, сортировкой, `JOIN` и
`GROUP BY`.

## Что сделано

- `db/schema.sql`: таблицы `disciplines`, `users`, `retake_requests`; первичные
  ключи, внешние ключи, ограничения для ролей, статусов, номера, заголовка и
  описания. `id` и `number` генерируются PostgreSQL identity-столбцами;
  seed синхронизирует счётчики после вставки демонстрационных значений.
- Добавлены индексы по `status` и `discipline_id` с комментариями о запросах,
  которые они ускоряют.
- Схему можно применять повторно: в начале скрипта таблицы удаляются в порядке
  от главной к справочникам. Скрипт предназначен только для отдельной учебной
  БД.
- `db/seed.sql`: два пользователя, две дисциплины и шесть заявок. В данных
  представлены все четыре статуса: `New`, `InProgress`, `Closed`, `Cancelled`.
- `db/queries.sql`: выборка новых заявок с сортировкой, соединение с
  дисциплинами, подсчёт по статусам и закомментированный пример проверки
  запрета статуса `Done`.
- В `docs/data-model.md` добавлено поле `createdAt`, которому в SQL
  соответствует `created_at`; остальные имена столбцов сверены с моделью.

## Запуск

Создать отдельную учебную базу и выполнить файлы из корня репозитория:

```text
createdb course_retake_requests
psql -d course_retake_requests -f db/schema.sql
psql -d course_retake_requests -f db/seed.sql
psql -d course_retake_requests -f db/queries.sql
```

## Факты выполнения

Проверка выполнялась на PostgreSQL 17.12 в отдельной базе
`course_retake_requests` через `psql`.

| Проверка | Результат |
|---|---|
| `schema.sql` первый запуск | `CREATE TABLE` × 3, `CREATE INDEX` × 2, код 0 |
| `schema.sql` повторный запуск | снова `CREATE TABLE` × 3 и `CREATE INDEX` × 2, код 0 |
| `seed.sql` | `INSERT 0 2` (пользователи), `INSERT 0 2` (дисциплины), `INSERT 0 6` (заявки) |
| Фильтр `status = 'New'` + сортировка | 2 строки: № 1002 от 11.11.2026, затем № 1001 от 10.11.2026 |
| `JOIN` с дисциплинами | 6 строк, в каждой заполнено `discipline_name`, а не только `discipline_id` |
| `GROUP BY status` | 4 группы: `Cancelled` — 1, `Closed` — 1, `InProgress` — 2, `New` — 2 |
| `CHECK` со статусом `Done` | отказ: `ERROR 23514`, ограничение `retake_requests_status_check` |
| `CHECK` со статусом `new` | отказ: `ERROR 23514`, ограничение `retake_requests_status_check` |
| Внешний ключ на несуществующую дисциплину | отказ: `ERROR 23503`, ограничение `retake_requests_discipline_id_fkey` |
| Число строк после отклонённых вставок | по-прежнему 6 — ошибочные данные не сохранились |
| Перезапуск сервера | 2 пользователя, 2 дисциплины, 6 заявок; сводка по статусам не изменилась |

Индексы в базе после выполнения схемы:

```text
retake_requests_pkey
retake_requests_number_key
retake_requests_status_idx
retake_requests_discipline_id_idx
```

Ограничения главной таблицы включают первичный ключ, уникальность `number`,
два внешних ключа на `users` и внешний ключ на `disciplines`, а также `CHECK`
для статуса, номера, заголовка и описания.

## Проверка клиента и API

Код ЛР9 не меняет клиент и сервер из ЛР8, поэтому дополнительно проверено,
что они не сломаны:

- `npm run build` во `frontend` — сборка Vite успешна, 38 модулей.
- `dotnet build` в `backend` — 0 предупреждений, 0 ошибок.
- Сценарии API ЛР8 на запущенном сервере: создание — `201`, короткий
  `title` — `400`, несуществующий id — `404`, `InProgress` без назначения —
  `409`, назначение исполнителя и переходы `New → InProgress → Closed` —
  `200`, недопустимый статус `Done` — `400`.

При этой проверке обнаружено расхождение примера в `docs/api-contract.md`:
`TimeOnly` в API принимает время с секундами (`14:30:00`), а в примере было
`14:30`. Пример исправлен; коллекция Postman уже использовала `14:30:00`.

## Безопасность данных

Пароли не добавлялись. Значения `password_hash` в демонстрационных
пользователях — явные заглушки, не являющиеся реальными хешами и не
пригодные для входа. Схема предназначена для отдельной учебной базы.

## Результат и границы

SQL-файлы проверены на реальном PostgreSQL, ограничения и повторный запуск
схемы работают. Временный учебный кластер использовался только для проверки и
после неё удалён; в репозитории нет ни дампа, ни паролей.

ЛР9 не подключает PostgreSQL к C# API: backend из ЛР8 по-прежнему хранит
заявки в памяти и не заполняет `created_at` и `created_by_user_id`. Интеграция
приложения с базой данных выполняется в следующей работе.
